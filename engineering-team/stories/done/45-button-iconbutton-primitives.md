# Story 45: `Button` and `IconButton` primitives, the bespoke-button migration, and the no-raw-`<button>` guard

**Status:** Done
**Created:** 2026-06-03
**Type:** Refactor (reclassified to a deliberate visual-change story per ADR 0045 Option 3)

## Background

This is epic story 8 of Epic 0001 (Overhaul-ready design system, `@unbnd/ui`), and it is the **first structural story** of the epic. Stories 38 to 44 laid the token foundation; this story is the first to build a real primitive component on top of it. ADR 0038 (Accepted, 2026-06-03) is the umbrella decision.

Seven foundations it depends on are already merged. Story 38 stood up the `@unbnd/ui` package (React peers, no build step, raw `src` export consumed by `apps/web` through Vite's bundler resolution) and relocated the token sheet to `packages/ui/styles/tokens.css`. Story 39 stood up the Playwright visual-regression harness with committed baselines and a CI `visual` job that fails on any pixel diff; that harness is the zero-diff gate this story is held to. Stories 40 to 44 carried the two-tier-token-plus-guard pattern across color, type, spacing, radii/elevation/z-index/breakpoints, and motion, each leaving a green guard under `packages/ui/test/` (mirroring `packages/trust/test/architecture.test.ts`) and each producing a refining ADR (0040 to 0044). Those stories also established the `@unbnd/ui` source-module precedent this story extends: the `GENRE_PALETTE` and `SEMANTIC_COLORS` exports in `packages/ui/src/palette.ts` / `colors.ts` and the `breakpoints` export in `breakpoints.ts`, all surfaced from `packages/ui/src/index.ts`. The package has **no `components/` layer yet**; this story creates it.

The audited and re-verified current state motivates the work (ADR 0038 §"Verified current state", "Primitives"; re-confirmed against `main` today):

1. **No primitive layer.** `@unbnd/ui` ships tokens and TS color/breakpoint modules, but zero React primitives. App code builds every interactive button by hand.

2. **38 raw `<button>` elements with bespoke per-site classes.** The count is confirmed at 38 against `main` today, spread across 21 files (15 components, 6 routes). Each `<button>` carries a one-off class authored at its call site, and there is no shared component, so a button restyle is a 38-site sweep with 38 chances to diverge. ADR 0038 §2 names exactly this: "Button (replaces the 38 raw `<button>`s and their nine bespoke classes)."

3. **One polymorphic button-or-link.** `apps/web/src/components/CallToAction.tsx` renders a `<Btn>` that is an `<a>` when a `ctaHref` is passed and a `<button>` otherwise, both carrying the `cta-btn` class. This does not appear in a raw-`<button>` grep, and it is the link-vs-button ambiguity ADR 0038 and this story's scope fence must resolve (see open questions).

ADR 0038 §2 ("Primitive component library in `@unbnd/ui`") sets the target: primitives expose **stable prop contracts** whose internals are swappable without changing callers; `Button` replaces the raw `<button>`s and their bespoke classes; `IconButton` covers icon-only buttons. The variant/size/state API is "a small, explicit, typed prop surface, not an open `className` escape hatch": `variant` is `"primary" | "secondary" | "ghost" | "danger"`, `size` is `"sm" | "md" | "lg"`, and state (`disabled`, `loading`, `aria-pressed`) rides on real props, "never bespoke per-site classes." The §2 rule on `className` is explicit and load-bearing for this story: **"A `className` prop, if allowed at all, is additive layout-only and never a way to re-skin."** ADR 0038 §6 names the guard: **"No raw `<button>` / `<svg>` in app code (must go through `Button` / `Icon`); allowlist names the registry/primitive files only."** The epic story-8 line scopes this story's half of that guard to **no raw `<button>`** (the `<svg>` half is epic story 9 / repo Story 9's icon registry). The guard is a Vitest test under `packages/ui/test/`, mirroring the Story-40 to 44 guards.

The epic's operating principle is "same pixels, better structure." This story is behavior-preserving: every migrated button keeps its current appearance, click handler, `type`, `disabled`/`aria` state, and label. House-rule anchors: `CLAUDE.md` "Brand tokens are the visual source of truth" (the primitives reference only the existing semantic tokens; they mint no new ones) and "No new lint/typecheck/build tooling without an ADR" (this story adds no tooling; the guard is a Vitest test under the existing `pnpm -r test`). Governing ADR: 0038. A refining ADR is expected, because the prop-contract design, the variant-to-archetype mapping, the resolution of the divergent buttons, and the guard's raw-`<button>` detection are real design calls (see open questions).

### The central tension: zero-diff vs normalize (the defining constraint, and the #1 Architect question)

The bespoke buttons were authored independently and do not all share one clean visual definition. There are two paths, and this story's default is the first:

- **(A) Zero-diff (preferred, consistent with the whole epic).** The primitive reproduces each existing button's **current pixels exactly** through its variant/size/prop mapping, so the Story-39 `visual` job stays zero-diff and no baseline is updated. Any genuine visual **normalization** (making inconsistent buttons consistent) is a **separate, later, intentional visual-change story** with a labeled baseline update and design review.
- **(B) Normalize now.** A visual change that requires baseline updates and design review. **Not this story.**

This story is **(A)**. The survey below shows the buttons cluster into a handful of archetypes that map well onto the §2 variant set, but several buttons carry per-site deltas (different ink color on the amber fill, a non-standard radius token, ink-filled rather than amber-filled "primary" actions, per-site padding and weight). Each such delta is one of three things, and the Architect decides which, per button: (a) a real `variant`/`size`/state distinction the API already expresses, (b) a one-off the primitive reproduces exactly (additive layout-only `className`, or a narrow extra prop, never a re-skin), or (c) a button that genuinely cannot be reproduced zero-diff by a clean variant. **Any case (c) must be called out explicitly for a decision (reproduce exactly vs normalize-with-baseline-update) and never silently normalized.** The Story-39 gate is the backstop: if the migration drifts a single pixel, the `visual` job fails, and that failure is investigated, not re-baselined.

### The button survey (counts and archetypes)

38 raw `<button>`s plus the one polymorphic `cta-btn` `<Btn>`. Grouped by visual archetype (the bespoke class is named; this is the PO's grounding read, not the final variant map, which is the Architect's call):

- **Primary, amber fill (→ `Button variant="primary"`).** `auth-submit` (`AuthForm.css`), `sub-submit-btn` (`Submit.css`), `rate-submit` (`RatingControl.css`), `foryou-invite-btn` (`Shelf.css`), `follow-follow` (`FollowButton.css`), `set-save` (`Settings.css`), and the polymorphic `cta-btn` (`CallToAction.css`). All are amber-background filled CTAs. **Divergences inside this cluster (the zero-diff risk):** `set-save` sets `color: var(--u-night)` and `foryou-invite-btn` sets `color: var(--u-ink)`, while the others use `color: var(--u-parchment)`; padding and font-weight vary per site (`semibold` vs `medium`, `space-9`/`-10`/`-12` insets). These are the deltas a clean `variant="primary"` must either express through `size` or reproduce exactly.
- **Secondary / outline (→ `Button variant="secondary"`).** `auth-btn-secondary` (`AuthForm.css`), `set-clear` (`Settings.css`), `search-more-btn` (`Search.css`), `cs-promote` (`CommunitySubmissions.css`), `copy-btn` (`CopyButton.css`), `pov-btn` (`PoVBar.css`), `rp-personalize` (`RatingsPanel.css`), `claim-btn` (`ClaimControl.css`), `follow-following` (`FollowButton.css`). Transparent or surface background, 1px border, ink/amber text. **Divergences:** `claim-btn` uses `border-radius: var(--u-radius-7)` where the others use `--u-radius`; border color varies (`--u-border`, `--u-border-hover`, `--u-ink-tint-20`, `--u-amber`).
- **Inverted-ink "primary" (→ Architect decides: a third primary tone or a reproduced one-off).** `tagc-apply` (`TagControl.css`) and `shelfc-add` (`ShelfControl.css`) fill with `background: var(--u-ink)` and `color: var(--u-surface-card)` rather than amber. These read as primary actions but are not amber, so they do not map cleanly onto `variant="primary"`. This is the clearest zero-diff-vs-clean-variant decision point.
- **Ghost / text (→ `Button variant="ghost"`).** `acct-signout` (`AccountMenu.css`), `searchbox-seeall` (`SearchBox.css`), `rp-tab` (`RatingsPanel.css`), `pov-sw` (`PoVBar.css`). No border, transparent background, text-forward; several are tab/toggle controls carrying an `-on`/`-active` selected class and `aria` state. `acct-signout` shows a red hover (a danger **state**, not a danger variant).
- **Link-styled text (→ Architect: `Button variant="ghost"`/link, or leave as-is per the link-vs-button fence).** `auth-linklike` (`AuthShell.css`, `text-decoration: underline`, no border/background/padding) and `sub-back` (`Submit.css`, a back-affordance with no border/background). These are real `<button>` elements today (so in scope), but they are styled as links; the Architect confirms whether they become a ghost/link `Button` or stay as bespoke text controls.
- **Pill / toggle (→ Architect: `Button` with a pill `size`/shape, or out of scope as a distinct primitive).** `gps-pill` (`GenrePillSelector.css`) and `rated-by-more` (`RatedByRow.css`) are pill-radius selectable controls. `gps-pill` carries `gps-on`/`gps-off` selected/disabled state classes. The §2 `Pill` primitive is epic story 10, not this story; the Architect decides whether these are `Button`s with a pill shape now or stay bespoke until story 10 (the PO's read: a selectable genre pill is plausibly the `Pill` primitive's job, not `Button`'s — flag for the Architect).
- **Icon-only (→ `IconButton`).** `acct-trigger` (`AccountMenu.css`, the avatar trigger, `padding: 0`, circle radius), `rate-star` (`RatingControl.css`, the star-rating buttons, `background: none`, icon glyph), `shelfc-remove` (`ShelfControl.css`, a remove "×" affordance), and `copy-btn` insofar as it pairs an icon with its label. These are the `IconButton` candidates; the Architect confirms which are truly icon-only (no text label) versus icon-plus-text (which stay `Button`).
- **No dedicated danger button.** There is no `variant="danger"` button on `main` today. Red appears only as a **state** (`follow-following.is-unfollow` turns the secondary red on the unfollow affordance; `acct-signout:hover` turns red). The §2 `danger` variant is part of the API contract but has no current call site to migrate; the Architect decides whether `danger` is defined now (for the contract) with these red-state buttons mapped to it, or whether they stay as state on their existing variant.

The read: the buttons cluster reasonably cleanly onto primary / secondary / ghost, but the inverted-ink "primary" pair, the per-site amber-fill ink-color and radius deltas, the link-styled text buttons, the pill/toggle controls, and the absence of a real danger button are the specific places where the clean-variant mapping and the zero-diff requirement can pull apart. Resolving each is the Architecture phase's core work.

## User-facing description

As an Unbnd engineer, I want typed `Button` and `IconButton` primitives in `@unbnd/ui` (a `variant`/`size`/state prop contract, token-backed, with no re-skin `className` escape hatch) and every one of the 38 raw `<button>`s plus their bespoke classes migrated onto them, with a CI guard forbidding raw `<button>` in `apps/web/src`, so that a future button restyle becomes one component edit instead of a 38-site sweep, the design-system primitive layer begins, and the gain is held by CI instead of by review vigilance.

This is developer-facing infrastructure. No Reader, Curator, or Author sees any difference; every button keeps its current appearance, label, and behavior, which the Story-39 visual-regression gate confirms is byte-identical.

## Out of scope

None of the following may grow into this story. The fence is the `Button`/`IconButton` primitives and the button migration only; it is a behavior-preserving refactor, not a redesign.

- **Visual normalization of the buttons.** This story reproduces every button's current pixels exactly (path A above). It does not make inconsistent buttons consistent, retune any color/padding/radius/weight, or unify the divergent amber-fill ink colors, the inverted-ink primaries, or the non-standard `claim-btn` radius. Each such change alters pixels, would fail the Story-39 gate, and belongs to a separate, intentional, design-reviewed visual-change story with a labeled baseline update. **This is the central constraint.**
- **Any `className` re-skin escape hatch.** Per ADR 0038 §2, the primitives expose a typed `variant`/`size`/state prop surface and no re-skin `className`. A `className` prop, if permitted at all, is additive layout-only and can never restyle the button. Re-introducing per-site skin through `className` would defeat the entire point of the primitive.
- **Any other primitive.** `Input`, `Field`/`Label`, `Card`, `Pill`, `Avatar`, and `Link` are epic story 10 (repo story TBD), not this story. The genre `gps-pill` and `rated-by-more` pill controls are flagged to the Architect precisely because a selectable pill is plausibly the `Pill` primitive's job; if so, they stay bespoke until story 10 rather than being forced into `Button` here.
- **The icon registry and the `<Icon>` abstraction.** ADR 0038 §3 and epic story 9 (repo Story 9) own `<Icon name>` and the no-raw-`<svg>` guard. This story builds `IconButton` (the button wrapper) but does **not** build the icon registry; the icons inside the migrated icon-buttons (the avatar, the star glyph, the remove "×") are carried across as they exist today and are migrated into the registry in story 9. The guard this story adds covers raw `<button>` only, not raw `<svg>`.
- **Layout primitives.** `Stack`, `Grid`, `Container` are epic story 12. No layout-primitive work here.
- **Any token change.** The token system is complete (Stories 40 to 44). This story mints no new color/type/spacing/radii/motion tokens; the primitives reference the existing semantic tokens. If a button's exact reproduction appears to need a value not in the token set, that is a signal of a divergence to escalate (open questions), not a license to add a token.
- **Non-button interactive elements.** Links (`<a>`), the `react-router` `<Link>`, and other non-button interactive elements are not converted. The one ambiguous case is the polymorphic `cta-btn` `<Btn>` (an `<a>` or a `<button>` depending on `ctaHref`); the Architect resolves it (open questions). Links merely styled as buttons stay as-is unless they are trivially a `<button>` already; ambiguous cases are flagged for the Architect, not silently converted.
- **Behavior, copy, or information-architecture change.** No button gains, loses, or changes a handler, label, destination, or `type`. The render must be byte-identical, proven zero-diff against the Story-39 harness with no baseline update.
- **Re-pointing the `CLAUDE.md` / `AGENTS.md` "brand tokens / primitives are the source of truth" doc rule or citing the new guard in the docs.** That is epic story 14 (repo Story TBD); this story leaves the docs as they are.

PRD §11.3 "Out of Scope" check: this story touches no product surface (no payments, file hosting, ebook sales, bounty marketplace, social feed, reading progress, federation, or notifications). It is behavior-preserving infrastructure and does not approach the §11.3 line.

## Open questions

For the Architect to resolve in the Architecture phase. The PO does not pick the prop names, the variant map, the CSS location, or the guard internals.

- **HEADLINE — zero-diff vs normalize, per divergent button.** The buttons cluster onto primary / secondary / ghost, but several carry per-site deltas: `set-save` (`--u-night` text) and `foryou-invite-btn` (`--u-ink` text) diverge from the `--u-parchment` amber-fill default; `claim-btn` uses `--u-radius-7` not `--u-radius`; `tagc-apply`/`shelfc-add` are ink-filled rather than amber; padding and weight vary across the amber-fill cluster. For each, the Architect decides whether the delta is (a) a real `variant`/`size`/state distinction the API expresses, (b) a one-off reproduced exactly (additive layout-only `className` or a narrow extra prop, never a re-skin), or (c) a button that genuinely cannot be reproduced zero-diff by a clean variant. **Any case (c) is escalated for a reproduce-exactly-vs-normalize-with-baseline-update decision and is never silently normalized.** This story's default is reproduce-exactly (path A); a deliberate normalization is a separate later story.
- **HEADLINE — the `className` rule.** ADR 0038 §2: the prop surface is `variant`/`size`/state, and a `className`, if allowed at all, is additive layout-only and never a re-skin. The Architect decides whether `Button`/`IconButton` accept a `className` at all, and if so, constrains it to layout (margin/grid placement) such that it cannot restyle the button. Where a call site today uses its class for both skin and layout (for example `.auth-btn-row .auth-submit` width rules), the Architect decides how the layout half is preserved without a skin escape hatch.
- **The exact prop-contract shape.** ADR 0038 §2 fixes `variant: "primary" | "secondary" | "ghost" | "danger"` and `size: "sm" | "md" | "lg"`. The Architect designs the full typed surface: how `Button` extends the intrinsic `<button>` props (so `onClick`, `type`, `disabled`, `aria-*`, `form` pass through), how `IconButton` differs (a required accessible label since there is no visible text, the icon child or an icon-name prop given the icon registry does not exist yet), how the `loading` state is expressed and rendered, and how selected/toggle state (`aria-pressed`, the `-on`/`-active` patterns on `rp-tab`/`pov-sw`/`gps-pill`/`follow-following`) is modeled as a prop rather than a class.
- **The variant-to-archetype map, including the gaps.** The Architect produces the authoritative map from each bespoke class to a `(variant, size, state)` tuple. Specifically: where the inverted-ink `tagc-apply`/`shelfc-add` land (a third primary tone, a reproduced one-off, or escalated as case (c)); whether `danger` is defined now with the red-state buttons (`follow-following.is-unfollow`, `acct-signout:hover`) mapped to it or whether red stays a state on their existing variant; and whether the link-styled `auth-linklike`/`sub-back` become a ghost/link `Button` or stay bespoke text controls under the link-vs-button fence.
- **The pill/toggle controls (`gps-pill`, `rated-by-more`).** The §2 `Pill` primitive is epic story 10. The Architect decides whether these selectable pill controls are `Button`s with a pill shape in this story or stay bespoke until the `Pill` primitive exists. The PO's read leans toward deferring a genre pill to `Pill`, but the call is the Architect's.
- **The polymorphic `cta-btn` `<Btn>` (button-or-link).** `CallToAction.tsx` renders an `<a>` or a `<button>` from one `<Btn>` depending on `ctaHref`. The Architect resolves whether the button branch becomes `Button` (with the link branch left as an `<a>` or handled by a later `Link` primitive in story 10), or whether the whole control is deferred, so the no-raw-`<button>` guard does not trip on the `<button>` branch while the migration stays honest about not converting the `<a>`.
- **Which icon-only buttons are truly `IconButton` vs icon-plus-text `Button`.** The Architect confirms which migrate to `IconButton` (no visible text: `acct-trigger` avatar, `rate-star`, `shelfc-remove`) versus stay `Button` with an icon-plus-label (`copy-btn`), and how each `IconButton` carries its accessible name (several already pass `aria-label`, for example `rate-star`'s `Rate ${n} of 5`).
- **Where the primitive CSS lives and how it ships.** ADR 0038 §7 says primitive CSS is co-located in `@unbnd/ui` and imported by the primitive (Vite handles the workspace CSS import). The Architect decides the file layout under `packages/ui/src/` (a `components/` directory the package does not have yet), how the CSS references the existing semantic tokens, and how it is bundled with no build step.
- **How the guard detects raw `<button>`, and the allowlist.** Mirroring the Story-40 to 44 guards (a `readFileSync` walk over `apps` + `packages` with `SKIP_DIRS` and a tight allowlist), the Architect decides how the guard recognizes a raw `<button>` JSX element (and whether it must catch the polymorphic `<Btn>`/dynamic-tag form and the `React.createElement("button", …)` form so a button cannot hide outside literal `<button>` syntax), and which files the allowlist exempts (the primitive source files in `@unbnd/ui` only, per ADR 0038 §6). The allowlist names only legitimate primitive-source files, per the AC.
- **Accessibility and focus-ring preservation.** Several buttons have specific focus/outline treatments (for example `follow-following.is-unfollow`'s `outline-color: var(--signal-negative)`), `aria-label`s, `role="menuitem"` (`acct-signout`), and keyboard semantics (`CopyButton` is explicitly a `<button>` "so it is keyboard-focusable and Enter/Space-activatable for free"). The Architect confirms the primitives preserve every button's current focus ring, `aria` semantics, role, and keyboard behavior exactly, so the migration is accessibility-neutral (or better) and zero-diff.
- **The `loading` state's render.** ADR 0038 §2 lists `loading` as a primitive state, but no button on `main` shows a loading affordance today (several use `disabled` while submitting, for example `auth-submit`, `acct-signout`, `search-more-btn`). The Architect decides whether `loading` is defined in the contract now (rendering nothing new by default, to stay zero-diff) or deferred, given that introducing a visible spinner would be a visual change.
- **Whether a refining ADR is warranted.** The PO's read is yes, as for Stories 40 to 44: the prop-contract design, the variant-to-archetype map (including the inverted-ink, danger, link-styled, and pill decisions), the zero-diff-vs-normalize resolutions, the `className` rule, and the guard's detection strategy are design choices worth recording on top of umbrella ADR 0038. The Architect confirms and writes it if so.
