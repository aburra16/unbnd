# Story 46: `Icon` registry — a typed `<Icon name>` over hand-authored SVGs, the inline-`<svg>` migration, and the no-raw-`<svg>` guard

**Status:** Done
**Created:** 2026-06-04
**Type:** Refactor (behavior-preserving, byte-identical; no visual change)

## Background

This is epic story 9 of Epic 0001 (Overhaul-ready design system, `@unbnd/ui`), the icon half of the §6 "no raw `<button>` / `<svg>`" pair whose button half shipped as Story 45. ADR 0038 (Accepted, 2026-06-03) is the umbrella decision; its §3 ("Icon abstraction") sets the target: one `<Icon name="search" />` backed by a registry of hand-authored SVGs, where the registry is a typed `name → SVG` map in `@unbnd/ui` and `name` is a string-literal union so a typo is a type error. §3 honors the standing **no-icon-library** rule (`AGENTS.md` §4, ADR 0038 "Constraints") — the registry holds OUR own SVGs, just centralized; the indirection is the point. Delivery is inline-SVG components, themeable via `currentColor` / token `fill`. §6 names the guard: "No raw `<button>` / `<svg>` in app code (must go through `Button` / `Icon`); allowlist names the registry/primitive files only." Story 45 / ADR 0045 built and locked the `<button>` half; this story builds and locks the `<svg>` half.

Foundations it depends on are merged. Story 38 stood up `@unbnd/ui` (React peers, no build step, raw `src` export consumed by `apps/web` through Vite's bundler resolution). Story 39 stood up the Playwright visual-regression harness with committed baselines and a CI `visual` job that fails on any pixel diff; that harness is the zero-diff gate this story is held to. Stories 40 to 44 carried the two-tier-token-plus-guard pattern across color, type, spacing, shape/breakpoint, and motion, each leaving a green guard under `packages/ui/test/architecture-*.test.ts` (mirroring `packages/trust/test/architecture.test.ts`). Story 45 added the `Button` / `IconButton` primitives, the `components/` directory under `packages/ui/src/`, and the no-raw-`<button>` guard (`packages/ui/test/architecture-button-literals.test.ts`). `IconButton` today takes its icon node as `children` (the raw `<Star>` node in `RatingControl.tsx`); its own doc comment records the intent that "when the icon registry lands (epic story 9) `children` becomes `<Icon name=…>` with no contract change."

The audited current state motivates the work (ADR 0038 §"Verified current state", "Icons"; re-confirmed against `main` today): **5 inline `<svg>` sites, one per file, across 5 files** — `SearchIcon.tsx`, `LogoMark.tsx`, `FollowButton.tsx`, `AuthMethodCard.tsx`, `RatingControl.tsx`. Two are standalone one-off icon components (`SearchIcon`, `LogoMark`); three are SVGs authored inline inside a larger component (`CheckGlyph` and `Star` are local functions; `NostrBolt` is an exported sibling of `AuthMethodCard`). There is no `<Icon>` indirection, so an icon-set swap touches every site, and a new raw `<svg>` can be added anywhere with nothing to catch it.

### The binding constraint: byte-identical, zero-diff (this is NOT a Story-45-style normalization)

Story 45's button work was a one-time, ADR-gated deviation: it reproduced the buttons' current pixels but accepted a deliberate normalization path under its own ADR. **This story does not repeat that.** The icon work is purely structural / modularity: invisible to users, no new icons, no icon redesign, no normalization, **zero-diff**. Every migrated icon must render byte-identical — same `viewBox`, same paths, same `stroke` / `fill` / `strokeWidth` / `strokeLinecap` / `strokeLinejoin`, same default size, same per-element opacity, same `aria` treatment — so the Story-39 `visual` job stays zero-diff and **no baseline is updated**. If any icon cannot be reproduced exactly by a clean registry API, that is an **escalation** to the Architect (reproduce-exactly-vs-something-else, with a recorded decision), never a silent normalization. The Story-39 gate is the backstop: a single-pixel drift fails the `visual` job, and that failure is investigated, not re-baselined.

The epic's operating principle holds: "same pixels, better structure." House-rule anchors: `AGENTS.md` §4 "No icon libraries … hand-crafted SVGs" (the registry IS that rule, centralized), `CLAUDE.md` "No new lint/typecheck/build tooling without an ADR" (this story adds no tooling; the guard is a Vitest test under the existing `pnpm -r test`), and the no-AI-slop rule for any string this work authors. Governing ADR: 0038 (§3, §6). A refining ADR is expected, as for Stories 40 to 45, because the registry shape, the `name`-union mechanism, the per-usage prop reproduction, the `IconButton` `children` question, and the guard's `<svg>` detection are real design calls (see open questions).

### The icon survey (count, identity, and reproducibility)

**5 raw `<svg>` sites → 5 distinct icons.** Each is a clean, self-contained, hand-authored SVG already in the codebase; each is reproducible. The four currently-`currentColor` icons are trivially themeable; `LogoMark` is the one with a non-trivial prop surface (per-element opacity). Grouped by identity (file, the icon's shape, its current props, its call sites — this is the PO's grounding read, not the final registry API, which is the Architect's call):

- **`search`** — `SearchIcon.tsx` (a standalone one-off component). A stroke magnifier: `viewBox="0 0 24 24"`, `fill="none"`, `strokeWidth={2}`, `strokeLinecap="round"`, `aria-hidden`, a `<circle cx=11 cy=11 r=7>` plus a `<path d="M21 21l-4.35-4.35">`. Props today: `size` (default 16) driving `width`/`height`, and `stroke` (default `SEMANTIC_COLORS.muted`). One call site: `SearchBox.tsx` (renders `<SearchIcon />`, all defaults).

- **`logo`** (the Unbnd brand mark) — `LogoMark.tsx` (a standalone one-off component). `viewBox="0 0 100 100"`, four shapes (two corner `<path>`s + two `<circle>`s), `role="img"`, an `aria-label` (the `title` prop). Props today: `size` (default 26), `fill` (default `SEMANTIC_COLORS.amber`), `opacityScheme` (`"solid"` | `"soft"`) which sets a `cornerOpacity` (1 vs 0.85) and a `circleOpacity` (1 vs 0.7) applied per element, and `title` (default `"Unbnd"`). **Four call sites with four distinct prop combinations**: `Nav.tsx` (`size=26`, solid), `Hero.tsx` (`size=48`, soft), `Footer.tsx` (`size=16`, `fill=SEMANTIC_COLORS.muted`, soft), `AuthShell.tsx` (`size=40`, `fill=logoFill`, soft). This is the richest prop surface; the registry API must reproduce all four exactly, including the per-element opacity scheme and the `aria-label`/`role="img"` treatment (the logo is NOT `aria-hidden`).

- **`check`** — `FollowButton.tsx`, the local `CheckGlyph()` function (an inline SVG, not an exported component). A two-segment checkmark: `viewBox="0 0 16 16"`, `width="14" height="14"`, a single `<polyline points="3.5,8.5 6.5,11.5 12.5,4.5">`, `fill="none"`, `stroke="currentColor"`, `strokeWidth="1.8"`, `strokeLinecap="round"`, `strokeLinejoin="round"`, `aria-hidden`, `className="follow-check"`. One call site: inside the `Following` state of `FollowButton`. The `className="follow-check"` (which positions/sizes the glyph alongside its label) must be preserved on the migrated `<Icon>` exactly.

- **`bolt`** (the Nostr lightning mark) — `AuthMethodCard.tsx`, the exported `NostrBolt()` component. `viewBox="0 0 24 24"`, `width="16" height="16"`, a single lightning `<path d="M13 2L4 14h6l-1 8 9-12h-6l1-8z">`, `fill="currentColor"`, `aria-hidden`. One call site: `AuthMethodSelect.tsx` passes `<NostrBolt />` as the `icon` prop of an `AuthMethodCard`. (Its sibling exports `EmailGlyph` / `GLetter` / `AppleLetter` are typographic `<span>` glyphs — `@`, `G`, `A` — NOT SVGs, so they are out of scope; see Out of scope.)

- **`star`** — `RatingControl.tsx`, the local `Star({ filled })` function (an inline SVG, not an exported component). `viewBox="0 0 24 24"`, `width="22" height="22"`, a single star `<path d="M12 2.5l2.9 5.9 6.5.95-4.7 4.58 1.1 6.47L12 17.9 6.2 20.9l1.1-6.47-4.7-4.58 6.5-.95z">`, `stroke="currentColor"`, `strokeWidth="1.4"`, `strokeLinejoin="round"`, `aria-hidden`, and a `fill` that toggles `"currentColor"` (filled) vs `"none"` (empty) on the `filled` prop. Five call sites, all inside `RatingControl`'s star row, each rendered as the `children` of an `IconButton` (`<IconButton …><Star filled={n <= score} /></IconButton>`). The filled/empty `fill` toggle is a per-usage variation the registry API must reproduce exactly.

**Read:** all 5 icons are clean, self-contained SVGs that reproduce byte-identically. `search` and `logo` are already standalone components (a direct lift into the registry); `check`, `bolt`, and `star` are inline / sibling SVGs that move into the registry and have their call sites repointed to `<Icon name>`. The only non-trivial reproduction surface is `logo`'s per-element `opacityScheme` and its `role="img"` + `aria-label` (it is not `aria-hidden`); the only per-usage value variation is `star`'s filled/empty `fill` toggle and the per-call `size`/`fill`/`stroke` props on `search` and `logo`. None requires a normalization; each is an exact lift. **`Avatar` is explicitly NOT an icon** (it renders initials or a picture, not a glyph) and stays as-is.

## User-facing description

As an Unbnd engineer, I want a typed `<Icon name="…" />` registry in `@unbnd/ui` — a `name` string-literal union backed by a map of our own hand-authored SVGs, themeable via `currentColor` / token `fill` and accepting size/color props that reproduce each current usage exactly — with all 5 inline `<svg>` sites (and the two one-off icon components, `SearchIcon` and `LogoMark`) migrated onto it and a CI guard forbidding any raw `<svg>` in `apps/web/src` outside the registry, so that a future icon-set swap is one file instead of N import sites, a typo'd icon name is a compile error, and the gain is held by CI instead of by review vigilance.

This is developer-facing infrastructure. No Reader, Curator, or Author sees any difference: every icon renders byte-identical — same `viewBox`, paths, stroke/fill/size, opacity, and `aria` treatment — which the Story-39 visual-regression gate confirms is zero-diff with no baseline update.

## Acceptance criteria

Testable from the outside.

- [ ] Given `@unbnd/ui`, when its exports are inspected, then it provides a typed `Icon` React component (exported from `packages/ui/src/index.ts`, mirroring the `Button` / `IconButton` / `SEMANTIC_COLORS` export precedent) backed by a registry of hand-authored inline-SVG components, one per icon, themeable via `currentColor` / token `fill`.
- [ ] Given the `Icon` `name` prop, when its type is inspected, then `name` is a string-literal union of the registered icon names (`search`, `logo`, `check`, `bolt`, `star`, or the Architect's final naming), so passing an unregistered name is a TypeScript error (`pnpm -r typecheck` fails on a typo'd `name`).
- [ ] Given `apps/web/src`, when it is searched for raw `<svg>` elements, then none remain outside the registry; every icon renders through `<Icon name=…>`. The five inline `<svg>` sites are migrated and the two one-off icon components (`SearchIcon`, `LogoMark`) are removed or reduced to a re-export of the registry, with their call sites updated.
- [ ] Given each of the 5 migrated icons, when it is rendered, then it is **byte-identical** to its pre-migration output: same `viewBox`, same child paths/circles/polylines, same `stroke` / `fill` / `strokeWidth` / `strokeLinecap` / `strokeLinejoin`, same default size, same per-element opacity (`logo`'s `opacityScheme`), and same `aria` treatment (`aria-hidden` for `search`/`check`/`bolt`/`star`; `role="img"` + `aria-label` for `logo`).
- [ ] Given each current call site's props, when migrated, then `<Icon name>` reproduces them exactly: `search`'s `size`/`stroke`; `logo`'s `size`/`fill`/`opacityScheme`/`title` across all four call sites (`Nav` 26 solid, `Hero` 48 soft, `Footer` 16 muted soft, `AuthShell` 40 `logoFill` soft); `check`'s `className="follow-check"`; `bolt` (defaults); `star`'s filled/empty `fill` toggle across its five `IconButton` children.
- [ ] Given `RatingControl.tsx`'s `IconButton` star buttons, when migrated, then the icon node passed as `children` is `<Icon name="star" …>` (per ADR 0045 / `IconButton` doc comment "with no contract change"), and `IconButton` is otherwise unchanged.
- [ ] Given the new no-raw-`<svg>` guard, when `pnpm -r test` runs, then it scans `apps/web/src` for raw `<svg>` elements (and dynamic / `createElement("svg")` forms), finds none, and passes; its allowlist names only the registry source files in `@unbnd/ui` (per ADR 0038 §6 "allowlist names the registry/primitive files only"), and it mirrors the Story-45 button-literals guard's structure.
- [ ] Given the prior guards (color, type, spacing, shape/breakpoint, motion, no-raw-`<button>`), when `pnpm -r test` runs, then they stay green (this story does not weaken or remove them).
- [ ] Given the workspace, when `pnpm -r typecheck` runs, then it passes (the new `Icon` `name` union and props included).
- [ ] Given the workspace, when `pnpm -r test` runs, then it passes, including the new no-raw-`<svg>` guard, all prior guards, and the existing web unit suite.
- [ ] Given the workspace, when the `apps/web` build runs (`pnpm --filter @unbnd/web build`), then it succeeds.
- [ ] Given the Story-39 `visual` job, when it runs against this story's change, then it is **zero-diff** against the committed baselines and **no baseline is updated**. If any icon genuinely cannot be reproduced byte-identical by a clean registry API, that is escalated for an Architect decision and never silently changed; a diff is investigated, not papered over by re-baselining.

## Out of scope

None of the following may grow into this story. The fence is the `Icon` registry, the 5-site migration, and the no-raw-`<svg>` guard only. It is a behavior-preserving, byte-identical refactor, not a redesign.

- **Any visual change.** This story reproduces every icon's current pixels exactly. It does NOT redesign an icon, retune a stroke / fill / size / opacity, add a new icon, normalize the icons toward one another, or change any `aria` treatment. Each such change alters pixels, would fail the Story-39 gate, and is not in this epic at all. This is the central constraint; this is NOT a Story-45-style normalization.
- **`Avatar`.** `Avatar` renders initials or a picture, not a glyph; it is not an icon and is untouched here. (Its palette is already token-sourced per Story 40; the `Avatar`/surface primitive itself is epic story 10.)
- **Any other primitive.** `Input`, `Field` / `Label`, `Card`, `Pill`, `Link` are epic story 10, not this story. `Button` / `IconButton` already shipped (Story 45) and are not re-designed here; `IconButton` only has its star `children` repointed from `<Star>` to `<Icon name="star">`, with no contract change.
- **The typographic glyphs.** `EmailGlyph` (`@`), `GLetter` (`G`), and `AppleLetter` (`A`) in `AuthMethodCard.tsx` are `<span>` text glyphs, not SVGs. They are not icons in the registry sense, are not raw `<svg>`, and are left exactly as they are. (Only `NostrBolt`, the one actual SVG among the `AuthMethodCard` exports, migrates.)
- **Any token change.** This story mints no new color / size / motion tokens; the icons reference `currentColor` and the existing `SEMANTIC_COLORS` exactly as they do today. If an icon's exact reproduction appears to need a value not already in use, that is a signal to escalate, not a license to add a token.
- **A sprite-sheet delivery.** ADR 0038 §3 allows a sprite sheet as an internal alternative the primitive could switch to later without changing callers; this story ships inline-SVG components (the existing form) and does not introduce a sprite pipeline.
- **Behavior, copy, or information-architecture change.** No icon gains, loses, or changes a handler, label, destination, or meaning. The render must be byte-identical, proven zero-diff against the Story-39 harness with no baseline update.
- **Re-pointing the `CLAUDE.md` / `AGENTS.md` "no icon libraries / brand tokens are the source of truth" doc rule or citing the new guard in the docs.** That is epic story 14 (repo Story TBD); this story leaves the docs as they are.

PRD §11.3 "Out of Scope" check: this story touches no product surface (no payments, file hosting, ebook sales, bounty marketplace, social feed, reading progress, federation, or notifications). It is behavior-preserving infrastructure and does not approach the §11.3 line.

## Open questions

For the Architect to resolve in the Architecture phase. The PO does not pick the registry shape, the `name` union mechanism, the prop names, the CSS / file layout, or the guard internals.

- **The registry shape and the `name`-union mechanism.** ADR 0038 §3 fixes the target (a typed `name → SVG` map, `name` a string-literal union so a typo is a type error, inline-SVG delivery). The Architect designs the concrete shape: where the map lives under `packages/ui/src/` (a new `icons/` directory, or alongside `components/`), whether each icon is a component or a render-able entry, how the union is derived (from the map's keys via `keyof`, or a hand-listed union) so it cannot drift from the registered set, and how `Icon` is exported from `index.ts` mirroring the `Button` / `IconButton` precedent.
- **How `Icon` props reproduce each current usage's size / color / state exactly.** The five sites have heterogeneous prop surfaces: `search` (`size`, `stroke`); `logo` (`size`, `fill`, `opacityScheme` driving per-element opacity, `title` → `aria-label`, `role="img"`); `check` (`className`, fixed 14×14, `currentColor`); `bolt` (fixed 16×16, `currentColor`); `star` (fixed 22×22, a `filled` → `fill` toggle, `currentColor`). The Architect decides whether `Icon` carries a uniform prop surface (e.g. `size`, `color`/`fill`, `className`, `title`, plus pass-through `aria-*`) that each icon's renderer interprets, or whether per-icon variant props (like `logo`'s `opacityScheme` and `star`'s `filled`) are modeled as icon-specific props — without breaking the single typed `<Icon name>` entry point and while reproducing all four `logo` call sites and the filled/empty `star` toggle byte-identical. The default sizes (16 / 26 / 14 / 16 / 22) and the `aria-hidden`-vs-`role="img"` split must survive.
- **Whether `IconButton`'s `children` become `<Icon>`.** ADR 0045 / the `IconButton` doc comment anticipate `children` becoming `<Icon name=…>` "with no contract change." The Architect confirms this happens here for the `star` (the only `IconButton` icon-child site on `main`) and that `IconButton`'s contract is genuinely unchanged. (The `acct-trigger` avatar `IconButton` child is an `Avatar`, NOT an icon, and is untouched.)
- **The guard's `<svg>` detection and allowlist.** Mirroring the Story-45 button-literals guard (comment-strip, `readFileSync` walk over `apps/web/src` with `SKIP_DIRS`, brace/string-aware opening-tag scan, plus the dynamic `createElement("svg")` form), the Architect decides how the guard recognizes a raw `<svg>` JSX element and any polymorphic / `createElement` form, and which files the allowlist exempts (the registry source files in `@unbnd/ui` only, per ADR 0038 §6). Unlike the button guard, there is no expected "deferred-class countdown" set — every one of the 5 sites migrates in this story, so the guard should reach zero offenders in `apps/web/src` with the allowlist naming only registry source.
- **Any icon that cannot be reproduced byte-identical by a clean registry API → escalate.** The PO's survey finds all 5 reproduce exactly, with `logo`'s per-element `opacityScheme` + `role="img"`/`aria-label` and `star`'s filled/empty `fill` toggle as the two non-trivial-but-reproducible surfaces. If the Architect finds any icon (or any per-usage variation) that a clean registry API cannot reproduce exactly, that is an **escalation** for a recorded decision, never a silent normalization. This story's default and requirement is byte-identical zero-diff.
- **Whether a refining ADR is warranted.** The PO's read is yes, as for Stories 40 to 45: the registry shape, the `name`-union mechanism, the per-usage prop reproduction (especially `logo` and `star`), the `IconButton`-children confirmation, and the guard's detection strategy are design choices worth recording on top of umbrella ADR 0038 §3 / §6. The Architect confirms and writes it if so.
