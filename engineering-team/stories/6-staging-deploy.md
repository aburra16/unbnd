# Story 6: Staging deployment (sovereign flow live on a real relay)

**Status:** Approved
**Created:** 2026-05-28
**Type:** Feature (infra)

## Resolved inputs (operator)

- Hostname: **`staging.unbnd.ink`** (operator adds the DNS A record → droplet IP).
- Droplet: **plain Ubuntu, no Docker** — the runbook installs Docker + compose first.
- Secrets: **generated by us and set via `gh secret set`**; librarian nsec handed to the operator out of band, never committed.
- Still needed at go-live: the droplet **IP** and an **SSH deploy key** installed on it (the workflow reads `DROPLET_HOST` + `SSH_PRIVATE_KEY` from GitHub secrets).

## Background

Stories 4 + 5a are on `main`: sovereign (NIP-07) login and the full sovereign rating write path (build template → client signs → server validates → publish to strfry → honest raw read-back). Everything has run only locally and in CI hermetic suites; the live-relay round-trip (AC-4/AC-5 of story 5a) is covered by a test gated on `STRFRY_TEST_URL` that has never actually run, because there is no deployed relay.

A DigitalOcean droplet and the `unbnd.ink` domain (Namecheap) are provisioned and idle. There is no way to deploy the apps yet: `docker-compose.yml` runs only the data layer (Tapestry = Neo4j + strfry + tapestry-api, Meilisearch, Postgres); there is no container/serve story for `apps/api` or `apps/web`, no TLS, and no CD.

This story stands up a **staging** environment — not a public launch — so the sovereign end-to-end flow can be exercised against a real strfry, closing the live-relay gap. Books remain fixtures; that is acceptable for staging. Custodial rating (story 5b) is not required — email users see the honest "coming for email accounts" note.

## User-facing description

As the Unbnd operator, I want the current `main` running on a staging hostname over HTTPS against a real relay, so that I (and trusted testers) can sign in with Nostr, rate the demo book, and see the rating publish and read back through the live stack — and so that future merges to `main` deploy automatically.

A tester visiting the staging URL sees the app over HTTPS, signs in with a NIP-07 extension, rates the demo book, and watches the rating persist and reappear on reload. Email signup/login works; the rating control shows the email-account placeholder.

## Acceptance criteria

Testable from the outside.

- [ ] AC-1: `apps/api` and `apps/web` build into deployable artifacts: a multi-stage Dockerfile for the API (pnpm build → `node dist`), and a static production build for the web app.
- [ ] AC-2: A `docker-compose.prod.yml` runs the full stack on one droplet — the data layer (incl. strfry), the API, and a reverse proxy serving the web build and proxying `/auth` + `/api` to the API.
- [ ] AC-3: The reverse proxy terminates TLS for the staging hostname with an automatically provisioned certificate; HTTP redirects to HTTPS.
- [ ] AC-4: Production config is supplied via env/secrets, never committed: `DATABASE_URL`, `BACKUP_ENCRYPTION_KEY`, `LIBRARIAN_PUBKEY`, `SEARCH_API_KEY`, `NEO4J_PASSWORD`, `POSTGRES_PASSWORD`, `PUBLIC_ORIGIN`. A committed `.env.production.example` documents every key with no secret values.
- [ ] AC-5: A librarian/house keypair is generated through the audited stack (Applesauce/nostr-tools, never hand-rolled); only the **hex pubkey** lands in config; the nsec is delivered to the operator out of band and never committed.
- [ ] AC-6: Migrations run automatically on API start (already the case) against the droplet Postgres; a fresh droplet comes up with the schema applied.
- [ ] AC-7: Pushing to `main` triggers a GitHub Actions job that builds and deploys to the droplet over SSH (`docker compose … up`), gated behind the existing CI passing. Secrets (SSH key, host, env) live in GitHub Actions secrets, not the repo.
- [ ] AC-8: On the deployed environment, a sovereign user can sign in, publish a rating, and read it back — the story-5a flow works end to end against the live strfry (verified manually and/or by running the gated integration test against the staging relay).
- [ ] AC-9: Cookies are `Secure` in production (HTTPS); the existing `isProduction` cookie path is exercised. (Full `__Host-` prefix + rate limiting remain cycle-5 hardening, out of scope here.)

## Out of scope

- **Public launch.** This is staging. Real book data/seeding, populated search, and a marketing-ready catalog are later work (books stay fixtures).
- **Custodial rating** (story 5b) — email users get the placeholder until it ships.
- **Security hardening** beyond `Secure` cookies: `__Host-` prefix, rate limiting, WAF, secrets manager — cycle 5.
- **Seeding real kind-39998 concept headers / book records** — only `LIBRARIAN_PUBKEY` is set so ratings address a consistent (if unseeded) book record. A seeding story comes later.
- **Multi-droplet / autoscaling / k8s** — one droplet, docker compose.
- **Monitoring/alerting/log aggregation** — basic container logs only for staging.
- **Zero-downtime/blue-green deploys** — a brief restart on deploy is acceptable for staging.

## Open questions

Resolved with the operator before/in the ADR.

1. **Staging hostname** — `staging.unbnd.ink` (recommended) vs apex/other. Operator confirms and creates the DNS A record → droplet IP.
2. **Droplet baseline** — Ubuntu with Docker + compose installed (DO Docker image) vs fresh; SSH user (`root` vs a `deploy` user). Determines provisioning steps in the runbook.
3. **Reverse proxy** — Caddy (auto-TLS, recommended) vs nginx + Certbot.
4. **Data-layer image availability** — is `unbnd/tapestry-data-layer:latest` pullable on the droplet, or does it need building/pushing first?
5. **Secrets handling** — generate values now and set them via `gh secret set` + the droplet `.env`, vs operator provides. Backup key + librarian key generated by us regardless.
