# Story 43: Two-tier radii, elevation, and z-index tokens, canonical breakpoints, and the guards

**Status:** Draft
**Created:** 2026-06-03
**Type:** Refactor

## Background

This is epic story 6 of Epic 0001 (Overhaul-ready design system, `@unbnd/ui`). ADR 0038 (Accepted, 2026-06-03) is the umbrella decision. Five foundations it depends on are already merged: Story 38 stood up the `@unbnd/ui` package and relocated the token sheet (it now lives at `packages/ui/styles/tokens.css`); Story 39 stood up the Playwright visual-regression harness with committed baselines and a CI `visual` job that fails on any pixel diff (that harness is the gate this story is held to); Story 40 established the two-tier-token-plus-guard pattern this story follows, introducing the two-tier color tokens, fixing the live token drift, and landing the first CI guards under `packages/ui/test/`; Story 41 carried that pattern up to the type axis (value-keyed raw tokens behind thin semantic aliases); and Story 42 carried it to spacing, including the multi-value-shorthand handling that this story's box-shadow case echoes. This story repeats that shape for four small, related axes at once: radii, elevation, z-index, and breakpoints.

These four axes are bundled because each is small (a handful of distinct values, unlike the 200-plus type and 355 spacing sweeps) and because the epic groups them as one story (epic sequence step 6). The audited and re-verified current state motivates the work:

1. **Radii are partly tokenized and the tokens are not on the two-tier model.** `--u-radius` (8px) and `--u-radius-lg` (12px) exist in `tokens.css` but sit outside the raw-plus-semantic structure Stories 40 to 42 established (they are single flat tokens, not a raw tier surfaced through semantic aliases). Against `main` today there are roughly 94 `border-radius` declarations across the web CSS: 27 already reference `--u-radius`, but many distinct literals remain (8px, 10px, 7px, 6px, 12px, 20px, 999px, 4px, 3px, 5px, 9px, 2px, the `50%` circular form, and at least one multi-value corner shorthand `0 0 7px 7px`). There is also literal duplication: a bare `8px` that equals `--u-radius`, and a `var(--u-radius, 8px)` fallback that hardcodes the same value a second time. The exact per-value breakdown is the Architect's and Implementer's to confirm; the PO does not enumerate it as a contract.

2. **Elevation is raw box-shadow literals.** Roughly 21 `box-shadow` declarations across the web CSS, around 15 distinct. Each is multi-value (offset-x, offset-y, blur, optional spread, color), and the color component already reads a token (`var(--u-ink-tint-*)`, `var(--u-amber-tint-*)`, `var(--u-parchment)`), but the geometry (the offsets, blur, spread, and the `inset` keyword) is literal. ADR 0038 §1 names elevation as `--u-raw-elevation-{0,1,2}` and frames it as "parchment-on-parchment depth, not drop shadows." This story tokenizes the existing shadows exactly as they are; it does not redesign them onto a parchment-depth model, because changing a shadow's geometry changes pixels and is out of scope (see Out of scope).

3. **z-index is a tiny set of raw literals.** Three distinct `z-index` values in the web CSS today (1, 40, 50). ADR 0038 §1 names a `--u-raw-z-{base,dropdown,sticky,modal,toast}` scale.

4. **Breakpoints are raw `@media` literals with no token or typed source.** Seven distinct `@media` pixel values appear in the web CSS today (480, 540, 620, 700, 720, 860, 880). ADR 0038's broader audit sketched "16-plus" ad-hoc breakpoints and floated collapsing them onto a `--u-raw-bp-*` set; the count on `main` is smaller, and the collapsing is explicitly out of scope for this zero-diff story (see Out of scope and the central constraints below). There is no `--u-raw-bp-*` set and no typed `breakpoints` export.

ADR 0038 §1 ("Complete, themeable, two-tier token layer") names all four axes: `--u-raw-radius-{sm,md,lg,pill}`, `--u-raw-elevation-{0,1,2}`, `--u-raw-z-{base,dropdown,sticky,modal,toast}`, surfaced through semantic aliases (for example `--u-radius-control`); and `--u-raw-bp-{xs,sm,md,lg,xl}`. ADR 0038 §1 calls out the breakpoint special case in its own words: **"CSS custom properties cannot be used inside `@media` queries, so the canonical breakpoint values are ALSO exported as a typed TS constant `breakpoints` from `@unbnd/ui` for use in any JS-driven responsive logic and as the documented source the CSS `@media` values must match; a guard checks raw `@media` pixel values against the allowed set."** ADR 0038 §6 names the guards: "No raw `@media` pixel values outside the allowed breakpoint set," plus the literal guards covering raw radius and z-index outside the token layer (and, by extension of the §6 pattern, raw box-shadow geometry).

The epic's operating principle is "same pixels, better structure": the only acceptable visible change from this story is none, proven zero-diff against the Story-39 `visual` job, no baseline updated. Phase classification: Phase 2 platform hardening (extends PRD §2.11 / Block E), to be recorded in the post-Phase-2 PRD addendum. It changes no product behavior and no PRD claim. House-rule anchors: `CLAUDE.md` "Brand tokens are the visual source of truth" (this story extends that source to cover radii, elevation, and z-index) and "No new lint/typecheck/build tooling without an ADR" (this story adds no tooling; the guards are Vitest tests under the existing `pnpm -r test`, and the typed `breakpoints` export is plain TS in the existing package). Governing ADR: 0038. A refining ADR may be warranted, because the breakpoint canonicalization mechanism, the typed-export contract, the `@media` guard design, and the radii/elevation/z-index naming for a set of values that is not a clean scale are real design calls (see open questions).

### Two central zero-diff constraints (both are load-bearing)

**Constraint 1 — No consolidation (same lesson as Stories 40, 41, 42).** Mint one token per *distinct in-use value*. Do not rationalize radii, shadows, z-index, or breakpoints onto a "cleaner" scale (do not snap a 7px and an 8px radius together, do not round a 6px-blur shadow to 8px, do not collapse two near breakpoints). Any such change alters pixels or responsive behavior and is a separate, intentional visual-change story under the ADR 0039 visual-change discipline, not this refactor.

**Constraint 2 — The breakpoint blind spot (flag prominently).** The Story-39 `visual` harness captures a single viewport (1280x800). It does **not** prove zero-diff across responsive breakpoints, because it never renders the narrow viewports where the `@media` rules take effect. Therefore consolidating the distinct breakpoints (which the ADR's broader audit floated) would be a *responsive behavior change the harness cannot catch* and must not be done here. Story 43 tokenizes and canonicalizes the **existing distinct breakpoint values as-is**: it establishes them as the canonical set in one place (the typed `breakpoints` export plus the documented allowed set the guard enforces), and the CSS `@media` literals must match that canonical set value-for-value. It does not change which value any given `@media` query fires at. Reasoning about responsive behavior, not visual gating, is the protection for this axis; the breakpoint refactor must be argued correct, not merely shown green against a single-viewport baseline. A future multi-viewport baseline enhancement to the harness is worth noting as a follow-up (an Architect open question), but is not built here.

## User-facing description

As an Unbnd engineer, I want radii, elevation, and z-index modeled as two tiers in `@unbnd/ui` (raw value-keyed tokens behind thin semantic aliases) with the app CSS referencing only tokens, and the breakpoint values established as one canonical typed source (`breakpoints` in `@unbnd/ui`) that the CSS `@media` queries must match, all locked by CI guards, so that a future radius, shadow, depth, or breakpoint change becomes a token-or-constant change instead of a scattered literal sweep, and the gain is held by CI instead of by review vigilance.

This is developer-facing infrastructure. No Reader, Curator, or Author sees any difference; the rendered app is byte-identical before and after at the gated viewport, and the breakpoint refactor preserves the exact firing points of every responsive rule. The Story-39 visual-regression gate confirms the single-viewport render; the breakpoint canonicalization is additionally reasoned about because the harness does not exercise the narrow viewports.

## Acceptance criteria

Testable from the outside.

- [ ] Given `@unbnd/ui`, when the radii, elevation, and z-index tokens are inspected, then each is two-tier: a raw tier of literal values (per ADR 0038 §1 Tier-1 naming, following the Story-41/42 value-keyed-raw approach) and semantic aliases that reference the raw tier and never a literal. The app references the semantic tier.
- [ ] Given every distinct in-use radius, box-shadow, and z-index value today, when it is migrated to a raw token, then it is preserved exactly as-is; no near-values are consolidated onto a cleaner scale, so every resolved value stays byte-identical.
- [ ] Given the existing `--u-radius` / `--u-radius-lg` tokens, when the radii axis is reworked, then they are folded into the two-tier model (the Architect decides whether they are kept as semantic aliases or renamed), every `border-radius` in app CSS references a radius token, the literal-duplicate cases (the bare `8px` equal to `--u-radius` and the `var(--u-radius, 8px)` fallback) are resolved to a single source, and no raw `border-radius` numeric literal remains outside the token layer.
- [ ] Given the box-shadow declarations, when they are migrated, then each becomes an elevation token preserving its exact geometry (offsets, blur, spread, `inset` keyword) and its existing color-component token reference, with the resolved declaration byte-identical to today; multi-value and `inset` shadows are handled by the mechanism the Architect chooses (mirroring the Story-42 multi-value shorthand handling), and no raw `box-shadow` geometry literal remains outside the token layer.
- [ ] Given the breakpoint values, when `@unbnd/ui` is inspected, then a typed `breakpoints` constant exports the canonical set (the distinct in-use `@media` values, as-is) for JS-driven responsive logic, and this is the documented source the CSS `@media` values must match.
- [ ] Given the app CSS `@media` queries, when they are inspected, then every `@media` pixel value is a member of the canonical breakpoint set; no `@media` query fires at a different viewport than it does today (the canonicalization changes where the value is sourced and named, never the value itself).
- [ ] Given the new guard(s), when `pnpm -r test` runs, then they (a) find no raw `border-radius`, `box-shadow`-geometry, or `z-index` literal outside the token layer, and (b) find no `@media` pixel value outside the allowed canonical breakpoint set, and pass; the allowlist names only the legitimate token-source files.
- [ ] Given the Story-40 color guards, the Story-41 type guard, and the Story-42 spacing guard, when `pnpm -r test` runs, then they stay green (this story does not weaken or remove them).
- [ ] Given the workspace, when `pnpm -r typecheck` runs, then it passes (including the new typed `breakpoints` export).
- [ ] Given the workspace, when `pnpm -r test` runs, then it passes, including the new `@unbnd/ui` guards, all prior guards, and the existing web unit suite.
- [ ] Given the workspace, when the `apps/web` build runs (`pnpm --filter @unbnd/web build`), then it succeeds.
- [ ] Given the Story-39 `visual` job, when it runs against this story's change, then it is zero-diff against the committed baselines. No baseline is updated. If any screen diffs, that is a signal the refactor altered pixels and must be investigated, not papered over by re-baselining.
- [ ] Given the single-viewport blind spot, when the breakpoint canonicalization is reviewed, then it is argued correct by inspection (each `@media` value maps to the identical canonical value), not merely shown green against the 1280x800 baseline; no responsive firing point changes.

## Out of scope

None of the following may grow into this story. The fence is the radii, elevation, z-index, and breakpoint axes only, and it is a refactor, not a redesign.

- **Consolidation or rationalization of any of the four axes.** This story preserves every distinct in-use radius, shadow, z-index, and breakpoint value exactly as it is today. It does not snap near radii together, round shadow geometry, collapse z-index layers, or merge near breakpoints. Each such change alters pixels or responsive behavior, and either the Story-39 gate would correctly fail (radii, shadows, z-index at the gated viewport) or the change would silently alter responsive behavior the gate cannot see (breakpoints). A genuinely rationalized scale for any axis is a separate, intentional visual-change story under the ADR 0039 visual-change discipline. **This is the first central constraint.**
- **Collapsing the breakpoints.** Specifically called out because the ADR's broader audit floated it: collapsing the distinct `@media` values onto a smaller `--u-raw-bp-{xs,sm,md,lg,xl}` ramp is a responsive *behavior* change. The Story-39 harness captures a single viewport and cannot prove the narrow-viewport renders are unchanged, so a breakpoint collapse would be an unverified behavior change. It is deferred to a separate intentional story that establishes multi-viewport baselines first. This story canonicalizes the existing values as-is. **This is the second central constraint.**
- **Redesigning elevation onto the "parchment depth, not drop shadows" principle.** ADR 0038 §1 frames elevation as parchment-on-parchment depth. The shadows on `main` today are conventional drop shadows. Reconciling them with the parchment-depth principle changes their geometry, which changes pixels; it is a visual-change story, not this refactor. This story tokenizes the existing shadows verbatim.
- **Any other token axis:** color (Story 40, done), type (Story 41, done), spacing (Story 42, done), motion (durations, easings — epic story 7, next). Those are out. The token sheet's existing non-radii/elevation/z-index/breakpoint entries are left as they are.
- Primitives (`Button`, `IconButton`, `Input`, `Card`, `Pill`, `Avatar`, `Link`), the icon registry and `<Icon>` abstraction, the motion layer and `prefers-reduced-motion` handling, and layout primitives (`Stack`, `Grid`, `Container`). Later epic stories. The guard allowlist may anticipate later token-source files, but this story builds none of these.
- Authoring a dark theme or any second skin. ADR 0038 §1 requires the two-tier structure to admit one; building one is epic story 13.
- Any behavior, copy, or information-architecture change. The only visible change permitted is none: render must be byte-identical at the gated viewport, proven zero-diff against the Story-39 harness, and responsive behavior must be unchanged, reasoned about given the single-viewport blind spot.
- Adding, removing, or changing any radius, shadow, z-index, or breakpoint value. The migration preserves every resolved value exactly; it changes where the value is defined, not what it is.
- Re-pointing the `CLAUDE.md` / `AGENTS.md` "brand tokens are the source of truth" doc rule at `@unbnd/ui`, or citing the new guards in the docs. That is epic story 14; this story leaves the docs as they are.

PRD §11.3 "Out of Scope" check: this story touches no product surface (no payments, file hosting, ebook sales, bounty marketplace, social feed, reading progress, federation, or notifications). It is behavior-preserving infrastructure and does not approach the §11.3 line.

## Open questions

For the Architect to resolve in the Architecture phase. The PO does not pick names, scale shapes, or guard internals.

- **Breakpoint canonicalization without consolidation.** How to establish the existing distinct `@media` values as one canonical set without collapsing any of them. The Architect decides what "canonical" means mechanically here (every distinct value becomes a named member of the set, preserving its exact firing point) and how the CSS `@media` literals are tied to that set, given that `var()` cannot be used inside `@media`. This is the chief difference from every prior axis: there is no `var()` sweep for breakpoints.
- **The typed `breakpoints` export mechanism.** ADR 0038 §1 requires a typed `breakpoints` TS constant exported from `@unbnd/ui` as the JS-side source of the canonical values. The Architect decides its shape (a typed record, a `const` object with literal types, the key naming), how it relates to any `--u-raw-bp-*` CSS tokens (whether the CSS tokens exist at all given they cannot enter `@media`, and if they do, how they stay in lockstep with the TS constant), and whether any single-source-of-truth mechanism keeps the TS constant and the documented allowed set from drifting.
- **The `@media` guard design.** ADR 0038 §6 names "no raw `@media` pixel value outside the allowed set." The Architect decides how the guard parses `@media` queries (range and feature syntax, `min-width` / `max-width`, possible `(width >= …)` forms), what the allowed set is sourced from (the typed `breakpoints` constant, a sibling list, or both), and how it reports an out-of-set value. The guard must catch a stray new breakpoint without flagging the legitimate canonical ones.
- **Radii / elevation / z-index naming for a value set that is not a clean scale.** ADR 0038 §1 sketches `--u-raw-radius-{sm,md,lg,pill}`, `--u-raw-elevation-{0,1,2}`, `--u-raw-z-{base,dropdown,sticky,modal,toast}`, which assume tidy ramps. The in-use values may not match those cardinalities (more than three distinct radii, more than three elevations, exactly three z-index values today). Because byte-identical render forbids consolidation, every distinct in-use value must be addressable. The Architect decides the naming for each axis (value-keyed, t-shirt with honest off-ramp names, or another scheme) without implying a consolidation that did not happen, as Stories 41 and 42 resolved for their scales.
- **Whether elevation box-shadows are tokenized as-is.** The PO's read is yes: tokenize each existing shadow verbatim (geometry preserved, existing color-component token reference preserved), and do not redesign onto the parchment-depth principle here. The Architect confirms and decides the token granularity (one token per whole shadow, or a raw-geometry tier behind a semantic elevation alias).
- **Multi-value and `inset` box-shadow handling.** Box-shadows are multi-value (offset-x, offset-y, blur, optional spread, color) and some are `inset`; this mirrors the Story-42 multi-value spacing-shorthand problem. The Architect decides how the migration keeps the resolved declaration byte-identical (a whole-shadow token, per-component `var()` substitution, or another approach) and how the guard parses a `box-shadow` to tell a legitimate token reference from a raw geometry literal. The existing color-component `var()` references must be preserved.
- **Whether `--u-radius` / `--u-radius-*` are renamed or kept.** They predate the two-tier model. The Architect decides whether to keep them as the radii axis's semantic aliases (lowest churn, but they would need to point at a new raw tier) or rename them under the `--u-raw-radius-*` / `--u-<role>` convention (more consistent, more churn). Either is acceptable to the PO if render stays byte-identical and the literal-duplicate cases are resolved to one source.
- **Guard allowlist scope.** Mirroring the Story-40/41/42 guards, each new guard carries a tightly scoped allowlist. The Architect decides which files each exempts (the token sheet where the raw literals legitimately live, the `breakpoints` TS source, and any other legitimate token-source file), and how the radius/z-index guards treat any TS-side constants if they exist. The allowlist names only legitimate token-source files, per the AC.
- **Runtime-injected values in TSX.** Story 40's color case surfaced TS-side palette arrays and live drift. The Architect should check whether any radius, box-shadow, z-index, or breakpoint value is injected at runtime (inline styles in TSX, a TS constant, a `matchMedia` / `window.innerWidth` comparison against a hardcoded breakpoint, or a computed style) rather than living in CSS, and decide how the sweep and the guards handle that surface so a literal cannot hide outside the CSS the guard scans. This matters most for breakpoints, where JS-driven responsive logic is exactly what the typed `breakpoints` export is meant to serve.
- **A future multi-viewport visual baseline.** Given the single-viewport blind spot, the Architect should note whether a follow-up enhancement to the Story-39 harness (baselines at the narrow viewports the breakpoints fire at) is worth recording as future work, so a later breakpoint-consolidation story has a real gate. Not built here.
- **Whether a refining ADR is warranted.** The PO's read is plausibly yes, as for Stories 40, 41, and 42: the breakpoint canonicalization mechanism and typed-export contract, the `@media` guard design, the elevation-as-is decision, and the naming for non-clean scales are design choices worth recording on top of umbrella ADR 0038. The Architect confirms and writes it if so.
